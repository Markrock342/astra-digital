# API Gaps — FIFACORP Bank Phase 1

วันที่: 2026-11-10  
ผู้ตรวจ: Bank (frontend)  
ขอบเขต: สิ่งที่หน้า UX/UI และ Live Chat ต้องใช้ เทียบของที่มีใน `server/api-handler.mjs` และ `server/domain.mjs`  
แบงค์ไม่แก้ schema และไม่เพิ่มตารางเอง รายการด้านล่างคือของที่ต้องให้ Mark/Nott ตัดสินก่อนลง UI ที่พึ่งฟิลด์นั้น

`docs/modules/nott-gap-map.md` ยังเขียนว่า chat และ notifications ขาด ทั้งที่โค้ดแถว commerce ปัจจุบันมีตารางและ route แล้ว เอกสาร gap ของ NOTT ชุดนั้นใช้เป็นสถานะ Sprint เก่า ไม่ใช้เป็นสถานะแชทของรอบนี้

## Blocker B1 — POST ผ่าน Vite ถูกปฏิเสธ

ตรวจเมื่อ 2026-11-10 บน `npm run dev` (หน้าเว็บ `http://127.0.0.1:4330` proxy `/api` ไป `http://127.0.0.1:4331`)

กด «เริ่มทดลองเป็นเจ้าของร้าน» ที่ `/admin` แล้วหน้าขึ้นข้อความ «ไม่อนุญาตคำขอจากเว็บไซต์อื่น» ยิงซ้ำจากเครื่องเดียวกันได้ผลเดิม:

```http
POST /api/demo-merchant HTTP/1.1
Host: 127.0.0.1:4330
Origin: http://127.0.0.1:4330
Content-Type: application/json
X-Astra-Request: 1

{}
```

ตอบ `403` body `{"error":"ไม่อนุญาตคำขอจากเว็บไซต์อื่น"}`

จุดตรวจอยู่ใน `server/api-handler.mjs` ทุก `POST` ต้องมีหัว `X-Astra-Request: 1` แล้วเทียบ `Origin` กับ `url.origin` ของ request ที่ API เห็น `server/http.mjs` สร้าง URL จาก `Host` หลัง proxy ค่านี้เป็นพอร์ต `4331` แต่เบราว์เซอร์ส่ง `Origin` เป็นพอร์ต `4330` จึงไม่เท่ากัน `GET` ไม่โดนเงื่อนไขนี้ หน้าร้านและรายละเอียดสินค้าจึงเปิดได้

ผลที่ตรวจต่อไม่ได้ในรอบนี้: ล็อกอิน, สมัคร, เดโมลูกค้า, เดโมแอดมิน, สร้างออเดอร์, จ่าย sandbox, เปิดแชท, มาร์คอ่านแจ้งเตือน

แบงค์ไม่แก้การตรวจ session นี้เอง ขอให้ Mark/Nott ทำให้โหมด dev ที่เอกสารกำหนด (Vite `4330` + API `4331`) ผ่านได้ โดยที่ production ยังปฏิเสธ origin คนละเว็บไซต์อยู่

## ของที่มีและเรียกได้

สิทธิ์ใช้ session cookie `astra_session` ฝั่ง server ตรวจ role เอง client ส่ง role ไม่ผ่าน `withoutClientPrivileges`

### แชท

| Method | Path | สิทธิ์ | พฤติกรรมจริง |
|---|---|---|---|
| GET | `/api/chat/threads` | ผู้ใช้ที่ล็อกอิน | ลูกค้าเห็นห้องของตัวเอง staff/admin เห็นทุกห้องพร้อมชื่อและอีเมลลูกค้า |
| POST | `/api/chat/threads` | ผู้ใช้ที่ล็อกอิน | เปิดห้อง `OPEN` ของตัวเอง หรือใช้ห้องเปิดอยู่ใบล่าสุด แล้วแทรกข้อความแรกเป็น `USER` |
| GET | `/api/chat/threads/:id/messages` | เจ้าของห้องหรือ staff | คนอื่นได้ 403 ไม่พบห้องได้ 404 |
| POST | `/api/chat/threads/:id/messages` | เจ้าของ หรือ staff ที่ตอบห้องคนอื่น | ห้อง `CLOSED` ได้ 409 ข้อความยาว 1–1000 ตัวอักษรหลัง trim |

ตัวอย่างเปิดห้อง:

```json
POST /api/chat/threads
{ "body": "ต้องการช่วยเหลือเรื่องออเดอร์" }
```

ตอบ 201 มี `thread` และ `messages` เรียงเก่าไปใหม่ ฟิลด์ข้อความคือ `id`, `thread_id`, `sender_type` (`USER` | `STAFF` | `ADMIN` | `SYSTEM`), `body`, `created_at`

เทสที่มีอยู่: `tests/nott-ops.test.mjs` ครอบคลุมเปิดห้อง, staff ตอบ, คนนอกได้ 403, และ HTTP POST สร้างห้องได้ ไม่ได้ครอบคลุม unread ของข้อความ, retry ซ้ำ, หรือ rate limit

### แจ้งเตือน

| Method | Path | พฤติกรรมจริง |
|---|---|---|
| GET | `/api/notifications` | รายการของ user นั้น สูงสุด 100 รายการ มี `read_at` |
| POST | `/api/notifications/:id/read` | อัปเดตได้เฉพาะแถวของตัวเอง คนอื่นได้ 404 |

### คิวและของที่ซื้อ

| Method | Path | พฤติกรรมจริง |
|---|---|---|
| GET | `/api/queue/me` | คิวของลูกค้า มี `queueNumber` |
| GET | `/api/queue` | staff เท่านั้น ลูกค้าได้ 403 |
| GET | `/api/orders/:id` | เจ้าของ reservation เห็น `queueNumber` และ `codes: []` เจ้าของออเดอร์ `DELIVERED` เห็น `codes` ที่ถอดรหัสแล้ว คนอื่นไม่เห็นโค้ด |
| GET | `/api/staff/orders` | staff เห็นรายการรวมออเดอร์และ preorder พร้อม `queue_number` ไม่มี codes |
| GET | `/api/admin` | admin เห็นรายการออเดอร์รวม reservation แต่ select ไม่มี `queue_number` |

## ช่องว่างต่อบอร์ดแชท

| ID | ต้องการ | ของที่มี | ช่องว่างที่ต้องคุย |
|---|---|---|---|
| CHAT-01 | ลูกค้าส่งแล้ว Admin Inbox เห็น | POST สร้างห้องและ GET รายการห้องได้ | ไม่มีหน้า UI และรายการห้องไม่มีข้อความล่าสุดหรือเวลาอัปเดต |
| CHAT-02 | แอดมินตอบถูกห้อง ตามลำดับ | POST ข้อความ staff ได้ | ไม่มี realtime ลูกค้าจะเห็นคำตอบก็ต่อเมื่อฝั่ง UI ไป GET ใหม่ |
| CHAT-03 | refresh แล้วยังมีประวัติ | ข้อความอยู่ใน DB | ไม่มี UI ที่โหลดประวัติ |
| CHAT-04 | แยกห้อง กันข้ามบัญชี | 403 เมื่อไม่ใช่เจ้าของและไม่ใช่ staff | ใช้ได้ที่ API ต้องมี UI สองบัญชีมาพิสูจน์ |
| CHAT-05 | unread และสถานะอ่านของแชท | notification มี `read_at` | ตาราง `chat_messages` ไม่มีสถานะอ่าน |
| CHAT-06 | ส่งไม่สำเร็จแล้ว retry โดยไม่ซ้ำ | ทุก POST แทรกแถวใหม่ | ไม่มี idempotency key ของข้อความ |
| CHAT-07 | คนไม่มีสิทธิ์ถูกปฏิเสธ | มี 403/404 | UI ต้องโชว์ error จากข้อความ server |
| CHAT-08 | ไม่รัน script และกันส่งถี่ | `clean()` แค่ตรวจชนิดและความยาว | ไม่มี rate limit บน route แชท |

ฟิลด์ที่ Inbox ต้องใช้แต่ยังไม่มีใน `GET /api/chat/threads`: ข้อความล่าสุดและเวลา, จำนวน unread ต่อห้อง, หน้าถัดไปเมื่อประวัติยาว, ทางปิดห้อง

## ช่องว่างต่อบอร์ดหน้าร้าน

| ID | ช่องว่าง |
|---|---|
| UI-04 | หน้าออเดอร์ลูกค้าไม่ได้อ่าน `queueNumber` ที่มีอยู่แล้ว หน้า Admin ที่ใช้ `GET /api/admin` ไม่ได้เลขคิว |
| UI-05 | โค้ดถูกส่งเป็นอาเรย์สตริงให้เจ้าของเท่านั้น ยังไม่มีคู่ ID + Password แยกฟิลด์ |
| UI-06 | ไม่มี API โปรโมชั่นหรือฟอนต์ร้าน แจ้งเตือนในเว็บมีแล้วแต่ไม่มีหน้าเรียก |

วันปิดรับจองบนหน้าสินค้าเป็นข้อความใน JSX ไม่มีฟิลด์ใน product API

## สิ่งที่ขอให้ Mark/Nott ตัดสิน

0. **Blocker B1** ปลด `POST` ตอนรัน `npm run dev` โดยไม่เปิด origin คนละเว็บใน production
1. Unread ของแชทจะนับจาก notification หรือต้องมีสถานะอ่านรายข้อความ อย่างหลังต้องแก้ schema
2. กันข้อความซ้ำตอน retry จะใส่ `clientMessageId` ที่ unique ต่อห้องหรือไม่
3. จำกัดความถี่ส่งข้อความต่อผู้ใช้จะทำที่ server หรือไม่
4. เลขคิวบน Admin จะเพิ่มใน `GET /api/admin` หรือให้หน้าใหม่เรียก `GET /api/queue`
5. รูปแบบ credential ที่หน้าออเดอร์ต้องโชว์
6. โปรโมชั่นและชุดฟอนต์อยู่ในรอบนี้หรือไม่
